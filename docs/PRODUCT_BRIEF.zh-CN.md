# AIOS Context Compiler：一页产品说明

> 10 类任务、30 对真实 A/B 实验中，30/30 对总 Token 全部下降，平均减少 50.8%。

## 一句话

在编码 Agent 执行每个任务前，从项目规则、状态、决策、文件地图、Skills、Hooks 和 Memory 中，编译出本次任务真正需要的最小充分上下文。

## 为什么现有机制不够

Claude Code、Codex 和 OpenCode 已经支持项目指令、Skills、工具和会话历史，但它们主要解决“信息能否进入上下文”。真实使用中更困难的是：

- 当前任务应该使用哪些信息；
- 哪些规则是关键约束，哪些只是背景；
- 哪些旧知识已失效；
- 哪些工具和权限本次根本不需要；
- Agent 不知道自己缺信息时，如何在重大决策前主动补齐。

直接加载大文件的结果，是上下文越积越大，而正确性并不稳定。

## 产品机制

```text
1. Intent Pass
   用户消息 + 环境摘要 + 源文件目录
   -> 任务契约、关键假设、读取计划

2. Compile Pass
   只读取计划选中的文件片段
   -> Task Context Package + 来源 + 排除项

3. Execution Pass
   用户任务 + Context Package + 被选中的工具/权限
   -> 执行结果 + Trace + 写回候选
```

AIOS 负责流程、隔离、来源和观测；模型负责理解意图、判断相关性和蒸馏内容。关键约束不能只依靠提示词，应逐步编译为 Hook、Permission 或程序验证。

## 第一阶段不做

- 不先做通用 RAG、向量库或知识图谱；
- 不把 AIOS 的所有设想一次实现；
- 不先做复杂多 Agent 与模型调度；
- 不用人工预制答案冒充智能编译；
- 不把 Token 下降等同于任务质量提升。

## 如何判断有没有价值

围绕真实问题验证四件事：

1. **任务质量**：关键约束是否满足，任务是否一次完成。
2. **上下文质量**：关键事实是否召回，无关或过期信息是否进入。
3. **用户负担**：纠正、返工和人工介入是否减少。
4. **系统成本**：新增模型调用、Token 和时间是否值得。

## 当前进展

我们已经用真实模型调用验证：更小、更受控的 Context Package 可以显著节省 Token，并减少无关信息进入结果。下一阶段要把人工冻结 Package 升级为自动意图识别、文件选择和上下文编译，并进一步验证复杂任务的一次成功率。
