# AIOS Context Compiler

> 让编码 Agent 在每一步工作前，拿到更少但更正确的上下文。

[中文产品说明](docs/PRODUCT_BRIEF.zh-CN.md) | [English brief](docs/PRODUCT_BRIEF.en.md) | [我们正在找谁](COLLABORATE.md) | [在线演示](site/index.html)

## 问题

现在的编码 Agent 已经能读文件、调用工具并持续执行，但仍会反复出现：

- 关键规则明明存在，Agent 还是漏掉；
- 旧决策、错误经验和无关资料混入当前任务；
- `AGENTS.md`、Skills、Memory 和工具定义持续膨胀；
- Agent 不知道自己缺少信息，却能产出逻辑自洽但不符合用户意图的结果；
- 换会话或换 Agent 后，用户必须重新解释项目；
- 用户看不到每一轮模型实际收到了什么，无法判断错误来自模型还是上下文。

这不是简单的“窗口不够大”，而是模型外部知识没有被正确选择、组合、验证和更新。

## 核心假设

我们希望在 Agent 与外部知识之间增加一个 **Context Compiler**：

```text
用户任务
  -> 意图与任务契约
  -> 只查看上下文源目录和摘要
  -> 选择相关文件与片段
  -> 编译为可追溯的 Task Context Package
  -> 在受控上下文中执行任务
  -> 记录结果与写回候选
```

它不是把所有项目文件塞给模型，也不是先做一个通用 RAG。第一阶段要验证的是：

> 模型驱动的“先选择、再读取、再编译”是否能减少关键遗漏和无关干扰，同时控制 Token、耗时与用户返工。

## 第一阶段

第一阶段基于 OpenCode，接管一条可开关、可观测的上下文组装路径：

1. `Intent Pass`：只看用户消息、极简环境和源文件目录，输出任务契约与读取计划。
2. `Compile Pass`：只读取被选中的内容，生成短而可追溯的 Context Package。
3. `Execution Pass`：新执行阶段只接收任务、Context Package 和按需选择的工具/权限。
4. `Trace`：保留每轮真实输入、来源、Token、工具调用和验证结果。
5. `A/B Test`：与同版本、同模型、同任务的原生 OpenCode 严格隔离对照。

首批上下文源保持简单：

```text
AGENTS.md       稳定项目规则
HANDOFF.md      当前进度与待办
DECISIONS.md    已确认决策及理由
FILES_MAP.md    文件导航
skills/         可复用流程
hooks/          可确定性执行的约束
memory/         用户偏好、经验和错误模式
```

## 已有证据与边界

我们从本机五类 Agent 工具、项目记录和执行轨迹中审计了 2,033 条去重用户消息，归纳出 128 个真实使用问题。上下文编译器直接面对的首批问题见[研究依据](docs/EVIDENCE.md)。

已有实验只证明：人工冻结的最小 Context Package 可以显著减少输入 Token 和无关信息泄漏。它**没有证明**智能编译器能提升任务成功率，之前的多轮实现和 A/B Test 还暴露了固定上下文包、阶段未真正隔离、评分标准失真等问题。

因此，这是一个有充分问题证据、产品假设清晰，但核心技术效果仍需严谨验证的项目。我们不会把试验品包装成已验证产品。

## 寻找技术伙伴

优先寻找两类工程师：

- **Agent Runtime / OpenCode 工程师**：熟悉 TypeScript、Agent loop、模型消息、工具注入、插件或内核扩展。
- **Context / Evaluation 工程师**：熟悉上下文工程、信息检索、Agent eval、实验隔离和可复现实验。

可以从一次 45 分钟设计评审或一个两周原型开始，再决定开源共同维护、项目制合作或长期合伙。详情见 [COLLABORATE.md](COLLABORATE.md)。
